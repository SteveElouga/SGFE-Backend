# Évaluation de préparation — OWASP & SOC 2 (CC1-CC9)

**Système :** Système de Gestion de Facturation d'Eau (SGFE)
**Périmètre :** dépôts `SGFE-backend` (microservices Django + gRPC, gateway GraphQL Strawberry) et `SGFE-frontend` (Angular PWA)
**Date de rédaction :** 4 septembre 2026
**Auteur :** analyse assistée, méthode décrite en fin de document

---

## 0. Avertissement de portée — à lire avant toute autre section

**Ce document est un diagnostic technique de préparation (« readiness assessment »), pas une certification.**

Une certification SOC 2 — en réalité une **attestation** délivrée à l'issue d'un audit — ne peut être émise que par un **cabinet d'expertise comptable (CPA) indépendant et accrédité**, à l'issue d'un audit formel conduit selon les normes de l'AICPA (SSAE 18 / AT-C 105 et 205). Un audit de Type II exige en outre une **période d'observation réelle** (généralement 3 à 12 mois) pendant laquelle l'efficacité *opérationnelle* des contrôles est testée sur des preuves accumulées dans le temps — pas seulement leur existence à un instant T dans le code.

Aucune analyse de code, aussi rigoureuse soit-elle, ne peut se substituer à cet audit ni porter le nom de « certification ». Ce rapport :

- évalue l'état du **code source réel** des deux dépôts à la date ci-dessus, avec preuves `fichier:ligne` ;
- compare cet état aux référentiels **OWASP Top 10:2021**, **OWASP API Security Top 10:2023**, **OWASP ASVS** (niveaux 1 et 2), et aux **critères communs SOC 2 (CC1-CC9)** de l'AICPA ;
- a pour seul objectif de **préparer** une future démarche d'audit SOC 2 réelle, en identifiant les écarts à corriger et les preuves à commencer à accumuler ;
- ne constitue **en aucun cas** une garantie de conformité, une pré-certification, ou un substitut à l'avis d'un auditeur accrédité.

Le mot « certifié »/« certification » n'est employé nulle part dans ce document pour qualifier l'état du système.

## Référentiels utilisés (intitulés exacts vérifiés — voir §5 Sources)

**OWASP Top 10:2021** (10 catégories, `A01` à `A10`) :
A01 Broken Access Control · A02 Cryptographic Failures · A03 Injection · A04 Insecure Design · A05 Security Misconfiguration · A06 Vulnerable and Outdated Components · A07 Identification and Authentication Failures · A08 Software and Data Integrity Failures · A09 Security Logging and Monitoring Failures · A10 Server-Side Request Forgery (SSRF).

**OWASP API Security Top 10:2023** (10 catégories, `API1` à `API10`) :
API1:2023 Broken Object Level Authorization · API2:2023 Broken Authentication · API3:2023 Broken Object Property Level Authorization · API4:2023 Unrestricted Resource Consumption · API5:2023 Broken Function Level Authorization · API6:2023 Unrestricted Access to Sensitive Business Flows · API7:2023 Server Side Request Forgery · API8:2023 Security Misconfiguration · API9:2023 Improper Inventory Management · API10:2023 Unsafe Consumption of APIs.

**OWASP ASVS** — la version stable courante au moment de la rédaction est **ASVS 5.0.0** (mai 2025), qui restructure le référentiel en 17 chapitres (`V1` à `V17`) ; ce rapport ne mobilise que les chapitres pertinents pour une architecture 100 % API :
V2 Validation and Business Logic · V4 API and Web Service · V6 Authentication · V7 Session Management · V8 Authorization · V9 Self-contained Tokens · V11 Cryptography · V12 Secure Communication · V13 Configuration · V14 Data Protection · V16 Security Logging and Error Handling.
Les trois niveaux d'assurance sont cumulatifs : **Niveau 1** (assurance faible, contrôles vérifiables même de l'extérieur), **Niveau 2** (assurance standard, recommandé pour toute application traitant des données sensibles ou des transactions — c'est le niveau pertinent pour un facturier), **Niveau 3** (assurance élevée, applications critiques financières/santé/gouvernementales). Ce rapport vise le Niveau 1 en totalité et les exigences de Niveau 2 les plus critiques, comme demandé.

**SOC 2 — Trust Services Criteria (AICPA, 2017, points de focus révisés 2022)** — le critère **Security** (« critères communs », `CC1` à `CC9`) est le seul obligatoire pour tout rapport SOC 2 ; les autres catégories (Availability, Processing Integrity, Confidentiality, Privacy) sont optionnelles et choisies selon l'engagement :
CC1 Control Environment · CC2 Communication and Information · CC3 Risk Assessment · CC4 Monitoring Activities · CC5 Control Activities · CC6 Logical and Physical Access Controls · CC7 System Operations · CC8 Change Management · CC9 Risk Mitigation.

**Note sur les autres catégories TSC (hors périmètre principal, une phrase chacune) :**
- **Availability** — pertinent : le système a des exigences de continuité de service claires (facturation, encaissement) mais aucune haute disponibilité réelle n'est en place (PostgreSQL/Redis mono-instance ou PoC de réplication seulement, cf. `AUDIT_SGFE.md` §6.3/§8·N) — à auditer séparément si ce critère est retenu.
- **Processing Integrity** — pertinent et partiellement déjà couvert de fait par la rigueur `Decimal`/transactions/verrous documentée dans `AUDIT_SGFE.md` §2.1, mais non évalué ici en tant que critère TSC formel.
- **Confidentiality** — pertinent (données d'abonnés, montants) et recoupe largement CC6/C1.1 déjà traités ; non audité comme catégorie séparée.
- **Privacy** — pertinent (données personnelles d'abonnés, RGPD) mais le TSC Privacy a ses propres critères P1-P8 non couverts ici ; seule la substance RGPD (export/anonymisation) est vérifiée dans la grille CC ci-dessous.

## 1. Résumé exécutif

**Niveau de préparation honnête : un projet à la sécurité applicative nettement plus mûre que la moyenne d'un projet à ce stade, mais qui échouerait aujourd'hui un audit SOC 2 Type II sur un seul critère — CC7 (surveillance/détection d'incident) — et qui porte plusieurs écarts de configuration ponctuels mais réels qu'un auditeur relèverait immédiatement.**

Ce qui a été vérifié directement dans le code (pas dans la documentation, pas dans `AUDIT_SGFE.md`, même si ses affirmations se recoupent largement avec ce qui suit) montre un système où l'authentification, la gestion de session, le contrôle d'accès au niveau de la gateway, le chiffrement des sauvegardes, le RGPD (partiel), et le durcissement GraphQL/HTTP sont **réels, testés et actifs** — pas seulement documentés. C'est un socle rare à ce stade d'un projet.

**Ce qui bloquerait un audit SOC 2 Type II aujourd'hui, par ordre de gravité :**

1. **Aucune piste d'audit métier générique, aucune observabilité (CC7.2/CC7.3, OWASP A09, ASVS V16).** C'est le blocage le plus sérieux et le plus difficile à rattraper rétroactivement : un Type II exige des preuves accumulées sur une période d'observation, et il n'existe aujourd'hui — dans le code réellement présent sur la branche `develop` — ni `TracerProvider`, ni endpoint `/metrics`, ni journal `AuditLog` générique, ni logs structurés. Une PR (**#193**, *« feat(audit): piste d'audit SOC2 »*) est **ouverte et non fusionnée** au moment de la rédaction ; elle apporte un vrai `AuditLog` mais **seulement sur 2 services (facturation, paiement) sur 8**, avec une immuabilité base de données non effective dans la configuration Docker actuelle (le rôle applicatif reste propriétaire de la table), et exclut explicitement l'observabilité (OpenTelemetry/métriques). Même fusionnée, cette PR ne suffirait pas à lever le blocage.
2. **Des valeurs de secrets par défaut insécures, committées en clair dans `docker-compose.yml`, qui neutralisent le fail-fast du code Python.** Le cas le plus grave : `PII_ENCRYPTION_KEY` a une valeur de repli qui est une **vraie clé Fernet exploitable** (`docker-compose.yml:564`) — un déploiement qui oublie de positionner cette variable en production chiffre silencieusement les données PII avec une clé connue de quiconque lit le dépôt. `DJANGO_SECRET_KEY`, `INTERNAL_GRPC_KEY`, `POSTGRES_PASSWORD`, `WHATSAPP_INTERNAL_API_KEY` ont le même pattern à une échelle de gravité moindre.
3. **mTLS interne avec repli en clair silencieux.** Le mécanisme est réel et actif par défaut sous `docker compose up` (certificats montés, code de bascule vers TLS fonctionnel), mais si les 3 fichiers de certificats sont absents (volume mal monté, service lancé hors compose), le code retombe sur `add_insecure_port`/`insecure_channel` **sans aucun log d'avertissement** — un écart direct à ASVS V12 (refus explicite attendu, pas un repli silencieux).
4. **Aucune ré-autorisation par rôle utilisateur au niveau des services gRPC internes.** L'architecture repose entièrement sur la gateway comme unique point de décision RBAC (confirmé par un aveu explicite dans le code lui-même, `services/auth/comptes/services.py:193`) ; l'authentification service-à-service existe (secret partagé + mTLS), mais aucune défense en profondeur ne rattraperait un bug ou un contournement du contrôle de rôle côté gateway.
5. **Chiffrement des PII incomplet.** Seul le service Abonné chiffre ses champs PII (Fernet) ; les mêmes catégories de données (téléphone, e-mail) restent en clair dans `services/auth/comptes/models.py` et `services/notification/notifications/models.py` — et un abonné anonymisé y garde son numéro de téléphone en clair indéfiniment.
6. **RGPD partiel** : export et anonymisation sont réels et bien conçus, mais strictement limités au service Abonné — aucun mécanisme équivalent pour les utilisateurs internes (auth-service), et aucune politique de rétention/purge automatique nulle part dans le code.

**Ce qui est déjà solide et qu'un futur audit devrait pouvoir valider rapidement** : authentification (JWT RS256, rotation/blacklist des refresh tokens, verrouillage anti-bruteforce, OTP haché + plafonné), contrôle d'accès applicatif (RBAC systématique côté gateway, protection IDOR de l'espace abonné, guards frontend cohérents), validation métier critique (index compteur vérifié à la saisie et re-vérifié à la facturation), absence totale d'injection SQL (ORM pur), durcissement GraphQL (profondeur/alias/tokens bornés, introspection désactivée en production), rate limiting HTTP par IP + verrouillage de compte, chiffrement des sauvegardes (AES-256-CBC/PBKDF2 avec fail-fast réel), chaîne CI/CD supply-chain (SAST, scan de dépendances, Trivy, signature cosign, gate de couverture 80 %) au niveau production sur presque tous les workflows.

**Bilan chiffré indicatif** (grille §3, 4 référentiels confondus) : sur l'ensemble des catégories évaluées, la majorité sont ✅ Conformes ou 🟡 Partielles avec un écart précis et actionnable ; une seule catégorie est ❌ Non conforme sans ambiguïté (journalisation de sécurité / surveillance — OWASP A09, ASVS V16, SOC 2 CC7). Aucune catégorie n'a été jugée subie par une négligence non identifiée par l'équipe elle-même : chaque écart trouvé ici recoupe, précise ou nuance un constat déjà présent dans `AUDIT_SGFE.md`, jamais une découverte contredisant une affirmation de conformité totale non vérifiée.

## 2. Méthode de vérification

Chaque affirmation ci-dessous a été vérifiée par lecture directe du code source (pas de la documentation ni des affirmations de `AUDIT_SGFE.md`, utilisé uniquement comme point de départ à recontrôler) : six analyses spécialisées en parallèle (authentification/session, contrôle d'accès, cryptographie/secrets, journalisation/audit/observabilité, validation des entrées/injection/rate limiting, chaîne d'approvisionnement/RGPD) plus une vérification ciblée SSRF/consommation d'API externes, chacune avec citations `fichier:ligne` relues au moment de l'analyse (4 septembre 2026). L'historique Git (`git log`) et la liste des PR (`gh pr list`) ont été consultés pour ne pas se fier à un état figé de `AUDIT_SGFE.md` : une pull request en cours (**#193**, non fusionnée) touchant directement la piste d'audit a ainsi été identifiée et est signalée explicitement partout où elle est pertinente, sans être comptée comme livrée.
